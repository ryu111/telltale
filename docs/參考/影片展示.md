# README 展示影片／GIF：remotion vs 終端錄影工具

## 1. Remotion 是什麼

React 寫程式化影片；核心模型是 `useCurrentFrame()`——每個 frame 呼叫一次 React render，畫面必須是 frame 數的**純函式**，不是即時動畫（文件明講：動畫要從 `useCurrentFrame()` 推，不能用 `setState`／`requestAnimationFrame`，因為 render 時 DOM 是逐 frame 跳著算，沒有「經過的時間」）。[useCurrentFrame()](https://www.remotion.dev/docs/use-current-frame) · [Animating properties](https://www.remotion.dev/docs/animating-properties)

**授權**：雙軌制。個人／非營利／≤3 人的營利公司＝免費（含商用）；≥4 人的營利公司要買 Company License（remotion.pro，$25/seat 起，Enterprise 月付 $500 起）。telltale 是個人專案，目前落在免費層。[LICENSE.md](https://github.com/remotion-dev/remotion/blob/main/LICENSE.md) · [Company licenses 公告](https://www.remotion.dev/blog/company-licenses)

**輸出格式**：mp4／gif／webm／PNG 序列（`npx remotion render`）。[render CLI](https://www.remotion.dev/docs/cli/render)

**CI 無頭渲染**：官方支援，GitHub Actions 範例就是 checkout → npm i → `npx remotion render` → 上傳 artifact；runner 沒 GPU 要用 `--gl=swangle`（`angle` 在 Actions 上會失敗）。[Server-Side Rendering](https://www.remotion.dev/docs/ssr) · [--gl flag](https://www.remotion.dev/docs/gl-options)

**Claude Code / AI 整合**：repo 有 `.agents/skills/`，但那是給貢獻者改 Remotion 原始碼用的 skill（`add-bug`、`add-cli-option`…），**不是**給使用者「產生展示影片」的官方 skill。只查到第三方非官方 skill（agentpedia.codes、skills.sh），沒有官方「telltale 這種案例」的現成整合。[repo 目錄](https://github.com/remotion-dev/remotion)

## 2. 試衣間.html 能不能直接重用

不行，要改寫。`試衣間.html` 的模擬是 `performance.now()` 驅動的即時 tick（`simNow += dt`、`STEP_POOL` 的 duration 是毫秒），這正是 Remotion 文件點名不支援的模式：**只有 `useCurrentFrame()` 驅動的動畫能正確渲染，iframe／裸 `requestAnimationFrame`／`Date.now()` 這類靠真實時間的邏輯，逐 frame 截圖會跳幀、不連續**。[IFrame 限制](https://www.remotion.dev/docs/iframe)

做法（照對照關係）：
- `requestAnimationFrame` + `performance.now()` → `useCurrentFrame()` + `Sequence`。原本 `tick(dt)` 已經是純狀態機（`tasks`、`advance(t)`、`cam` 緩動都是資料），改寫成：每個 frame 用固定 `dt = 1000/fps` 呼叫既有的 `tick`／`advance`／`ease` 邏輯 N 次（frame 數 × fps 換算成累積 ms），得到那一 frame 的狀態，再渲染成 React 節點（原本組字串塞 `<pre>`，可以直接搬成 React，邏輯不用大改，只是驅動源從「真時間」換成「frame 迴圈跑決定性次數」）。工程量：中——狀態機本來就跟渲染分離，改的地方集中在驅動迴圈和輸出從 HTML 字串換成 JSX。

## 3. 替代方案：真終端錄影

| | VHS (charmbracelet/vhs) | asciinema + agg |
|---|---|---|
| 錄的是什麼 | 真終端（靠 `ttyd`＋`ffmpeg`），`.tape` 腳本化打字／等待／截圖 | 真終端 session（pty），存成文字格式 `.cast` |
| 能跑 `claude` 這種互動 TUI | 能，腳本可 Type／Enter／Sleep／Wait，錄的是真實終端輸出 | 能，`asciinema rec` 就是包一個 pty，跟跑什麼程式無關 |
| API 金鑰 | 不需要；但若腳本裡真的跑 `claude` 互動，就是真的呼叫，會吃額度、不是決定性的 | 同上 |
| CI | 官方有 GitHub Action、支援 Docker | 可以（`asciinema rec -c`），但沒有 VHS 那種宣告式腳本／官方 Action，時序要自己兜 |
| 輸出 | GIF／MP4／WebM／PNG 序列 | `.cast`（文字，體積小）→ 用 `agg` 轉 GIF（用 gifski），沒有原生 mp4 |
| 授權 | MIT | 開源 |

[VHS repo](https://github.com/charmbracelet/vhs) · [agg repo](https://github.com/asciinema/agg)

**評估**：要展示「真實 plugin 在 Claude Code 裡跑」，VHS 比 Remotion 更對題——Remotion 本身文件說它不適合截真實、非 frame 驅動的畫面（Claude Code TUI 正是這種）；VHS 直接錄真終端，是「這東西真的長這樣」的第一手證據。VHS 對 asciinema+agg 的優勢是宣告式 `.tape` 腳本＋官方 GitHub Action，比 asciinema 手動兜時序更適合重複產生／放進 CI。**缺點**：若腳本內容是真的跑 `claude`，demo 非決定性（LLM 回應、時間都會變）且耗真額度；更穩的做法是驅動 telltale 的 band.tsx 吃「假事件」（重用 試衣間.html 已經寫好的模擬事件序列，改成餵進真的 plugin render 而非 HTML mock），录出來的畫面才是每次一致的。

## 4. README 建議與最小可行流程

- **格式**：GitHub README 的 `<video>` 標籤在原始 markdown 裡會被過濾掉，不會播放；`.gif`／`.png`／`.webp` 用 `![]()` 直接內嵌會播放。要放 mp4，得把檔案拖進 GitHub 網頁的 Issue／PR／編輯框上傳，換來的 `github.com/user-attachments/assets/...` URL 貼進 README 才會渲染成 `<video>` 播放器（直接指本地 mp4 路徑不行）。GIF 沒有官方硬性大小上限，但檔案大會拖慢 README 載入，經驗值抓 5–10MB 內。
- **最小可行流程（建議 VHS 路線）**：
  1. 寫 `demo.tape`：設終端尺寸（如 150×40）、啟動一個跑著假事件序列的 telltale（重用 試衣間.html 的模擬邏輯，接到真 plugin 而非 HTML），排好 Type／Sleep 步驟。——2–4 hr（含調時序、配色）
  2. `vhs demo.tape` 本機跑出 `demo.gif`，肉眼校對。——0.5 hr
  3. 若要 mp4：改 tape 輸出 `.mp4`，或沿用 gif；mp4 要走上傳換 URL 那條路才能放 README。——0.5 hr
  4. （可選）接 VHS 官方 GitHub Action，tag 時重新產生 gif、當 release asset，README 永遠指到最新一份。——1–2 hr
  - **總工時估：約 1 個工作天（6–9 hr）**，多數時間花在「怎麼讓 telltale 吃假事件跑出好看的一段」而不是工具本身。
  - Remotion 路線（若要試衣間.html 那種精修過的宣傳動畫而非真機截圖）：另需 1–2 天把 tick 迴圈改寫成 frame-driven，屬於獨立子任務，不建議跟 VHS 這條混著做第一版。
